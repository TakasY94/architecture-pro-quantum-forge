# Анализ и Рекомендации по Инфраструктуре для RAG-Бота в QuantumForge Software

## Введение
QuantumForge Software — финско-эстонская компания с фокусом на SaaS-платформе для моделирования промышленных объектов ("Digital Twin") и консалтинговом направлении. Компания сталкивается с проблемами разрозненности документации (Markdown/MDX файлы, Confluence страницы, PDF-спецификации), дублирования контента, долгого поиска информации и устаревания материалов. Внедрение RAG-бота на основе Retrieval-Augmented Generation позволит сократить время поиска, повысить продуктивность, автоматизировать запросы, выявлять пробелы в документации и обеспечить масштабируемость.

Учитывая конфиденциальность данных (часть материалов не подходит для облака из-за GDPR и корпоративных политик), приоритет отдаётся решениям, позволяющим on-premise развёртывание. Анализ охватывает сравнение LLM-моделей, моделей эмбеддингов, векторных баз данных и серверной конфигурации. На основе этого предлагаются варианты инфраструктуры с выбором оптимального. Данные основаны на актуальных сравнениях на конец 2025 года.

## 1. Сравнение LLM-моделей: Локальные (Hugging Face) vs Облачные (OpenAI / YandexGPT)

| Критерий                  | Локальные Hugging Face (например, Llama 3.1/4, Qwen2, Mistral Nemo) | Облачные OpenAI (GPT-4o, GPT-4o mini, o1/o3 серии) | Облачные YandexGPT (YaGPT Pro/Lite) |
|---------------------------|---------------------------------------------------------------------|----------------------------------------------------|-------------------------------------|
| **Качество ответов**      | Высокое на открытых бенчмарках (85–92% на MMLU, GSM8K, HumanEval). Хорошо поддаётся fine-tuning под домен. Multilingual поддержка сильная у новых моделей, но уступает proprietary в сложном reasoning и нюансах. | Лидер рынка (92–97%+ на тех же бенчмарках). Лучшее понимание контекста, reasoning, креативность и обработка сложных задач. | Хорошее качество (88–93%), особенно сильное в multilingual (русский, финский, эстонский, скандинавские языки). Сопоставимо с GPT-4o в русскоязычных задачах, но слабее в глобальных. |
| **Скорость работы**       | 20–60 токенов/сек на хорошем GPU (A100/RTX 4090). Зависит от оптимизаций (vLLM, TensorRT-LLM). На CPU — значительно медленнее. | 80–200+ токенов/сек, низкая латентность, автоматическое масштабирование под нагрузку. | 70–150 токенов/сек, оптимизировано для низкой латентности в EU-регионах. |
| **Стоимость владения и использования** | Open-source — бесплатно. TCO = hardware (сервер/GPU от $5–20 тыс. разово) + электроэнергия и обслуживание (~$1–3 тыс./год). Нет платежей за токены. | Pay-per-token: $2.5–15 за 1M токенов (в зависимости от модели). Для 100 сотрудников с умеренной нагрузкой — $10–50 тыс./год. | Дешевле OpenAI (примерно 30–60% от цены OpenAI в EU). Subscription или pay-per-token, ориентировочно $5–25 тыс./год при аналогичной нагрузке. |
| **Удобство и простота развёртывания** | Средняя сложность. Требует DevOps-навыков (Docker, Kubernetes, Ollama/vLLM/Text Generation Inference). Легко fine-tune, но нужно управлять инфраструктурой. | Максимально просто — REST API, SDK для всех языков. Нет необходимости в инфраструктуре. | Просто (API), есть SDK. EU-хостинг и соответствие GDPR упрощают использование в Финляндии/Эстонии. |

## 2. Сравнение моделей эмбеддингов: Локальные (Sentence-Transformers) vs Облачные (OpenAI Embeddings)

| Критерий                       | Локальные Sentence-Transformers (например, all-MiniLM-L6-v2, multilingual-e5-large, bge-m3) | Облачные OpenAI Embeddings (text-embedding-3-large/small, ada-002 legacy) |
|--------------------------------|---------------------------------------------------------------------------------------------|--------------------------------------------------------------------------|
| **Скорость создания индекса**  | Средняя: 500–2000 документов/сек на CPU, до 5000+/сек на GPU. Для ~18 000 Markdown + 3000 Confluence + 250 PDF — 1–5 часов на хорошем сервере. Batch-processing эффективен. | Высокая: 5000–10 000+ документов/сек (API parallel calls). Индексация того же объёма — 10–40 минут. Масштабируется автоматически. |
| **Качество поиска**            | Хорошее (82–88% на MTEB leaderboard 2025). Отличная поддержка multilingual (bge-m3, e5). Поддаётся fine-tuning под домен компании. Немного уступает в нюансах семантики. | Отличное (88–92%+ на MTEB). Лучшее понимание контекста, длинных текстов и сложных запросов. Multilingual поддержка сильная, но чуть слабее в нишевых языках (финский/эстонский). |
| **Стоимость владения и использования** | Бесплатно (open-source). TCO = только инфраструктура (~$1–3 тыс./год на сервер). Нет платежей за токены. | Pay-per-token: ~$0.0001–0.0004 за 1K токенов. Для начальной индексации + прирост 400 страниц/мес — $500–2500/год. Нет начальных вложений в hardware. |

## 3. Сравнение векторных баз: ChromaDB vs FAISS

| Критерий                              | ChromaDB                                                                 | FAISS (Facebook AI Similarity Search)                                      |
|---------------------------------------|--------------------------------------------------------------------------|----------------------------------------------------------------------------|
| **Скорость поиска и индексации**      | Поиск: 20–80 мс/query (HNSW). Индексация: 1–3 сек/1000 векторов. Достаточно для <1M векторов и 100–200 одновременных запросов. | Поиск: 5–30 мс/query (IVF + HNSW + GPU). Индексация: 0.3–1 сек/1000 векторов. Лучше для больших датасетов (>1M) и высокой нагрузки. |
| **Сложность внедрения и поддержки**   | Низкая. Python-native, простой API, встроенная persistence, metadata filtering. Легко интегрируется с LangChain/LlamaIndex. Минимальный DevOps. | Средняя-высокая. C++ core + Python wrappers. Требует ручного выбора/тюнинга индексов (IVF, PQ, HNSW). Больше усилий на production-стабильность. |
| **Удобство в работе**                 | Высокое. Автоматическое сохранение, коллекции, querying с фильтрами из коробки. Отлично подходит для прототипов и корпоративных RAG. | Высокая гибкость, но raw-интерфейс. Удобно с обёртками (LangChain, Haystack), но требует больше кода для persistence и метаданных. |
| **Стоимость владения (учёт инфраструктуры)** | Бесплатно (open-source). Работает на commodity hardware (CPU + 64–128 GB RAM). TCO ~$2–4 тыс./год (сервер + энергия). | Бесплатно. Аналогично, но для максимальной скорости выгоднее GPU (+20–30% стоимости сервера). TCO ~$3–6 тыс./год. |

## 4. Рекомендуемая Конфигурация Сервера
Для RAG-бота (обработка ~18K docs, 400 pages/month, 100+ users):
- **CPU**: Multi-core (например, AMD EPYC/Intel Xeon 16-32 cores, 3.0+ GHz) для indexing/parallel queries.
- **RAM**: 64-128 GB (DDR4/5) для in-memory vectors (~10-20 GB на 1M embeddings).
- **GPU**: NVIDIA RTX 4090/A100/H100 (24-80 GB VRAM) для acceleration LLM/inference; или без GPU для лёгких моделей.
- **Storage**: 1-2 TB NVMe SSD для persistence.
- **Общий Setup**: Dedicated on-premise сервер (~$8,000-20,000 initial) с Docker/Kubernetes. Для теста — VM с 8-16 cores, 32-64 GB RAM.

**Лучший вариант: Вариант 1 (Полностью локальный с ChromaDB)**  
Аргументация: конфиденциальность критически важна (sensitive спецификации клиентов ABB/Wärtsilä), долгосрочная экономия на API, наличие сильной dev-команды в Таллине для поддержки on-premise решений. ChromaDB обеспечивает быстрый старт и простоту, а открытый стек позволяет в будущем fine-tune модели под домен компании и масштабировать на другие команды или даже продукт для клиентов.

## Выбор Векторной БД
Для создания бота планирую использовать **ChromaDB**.

Почему именно ChromaDB:
- Высочайшее удобство и низкая сложность внедрения — Python-native, отличная интеграция с LangChain/LlamaIndex, встроенная persistence и metadata filtering.
- Достаточная производительность для текущего и прогнозируемого объёма (<1M векторов, 100–200 одновременных пользователей).
- Минимальные затраты на инфраструктуру и поддержку.
- Легко прототипировать и итерировать, что важно для выявления пробелов в документации на ранних этапах.

FAISS рассматривается как возможный апгрейд в будущем при росте нагрузки, но на старте ChromaDB даёт лучший баланс скорости разработки и качества.
